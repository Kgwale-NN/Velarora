# Notepad model repair

The original `run_20261116_194022` used the Notepad-Practice collection: three training pictures (two positives and one negative), two validation pictures and two test pictures. Its high validation score came from a tiny same-PC sample and does not establish accuracy on other screens. Both the original PT checkpoint and ONNX inference falsely identified the clean Velarora login page as Notepad at approximately 91% confidence. A closed dashboard also produced a false detection. Increasing confidence alone would not remove the login error without risking missed real windows.

The repair workspace is private under `data/datasets/notepad-repair`. Review candidates were sampled from saved local events. Foreground process metadata and the old model's predictions were not used as ground truth: several events marked notepad.exe actually showed a browser, and some marked chrome.exe showed Notepad. Pictures were visually reviewed before assigning labels. Unknown or potentially sensitive text was excluded from the selected positive examples.

The new label policy is the actual visible Notepad window including title and menus, excluding the Windows taskbar. A Notepad icon, Task View thumbnail or screenshot embedded in another app is not labelled as an active Notepad window. This visual policy still cannot prove which Windows process is running; browsers supply shared pictures, not process telemetry.

The first repair split contains 58 training images: 10 reviewed actual positive screenshots, 18 reviewed negatives/crops, and 30 synthetic training-only placements of reviewed Notepad windows on reviewed backgrounds. Validation has 3 positive and 3 negative images. Test has 6 positive and 6 negative images, including the supplied closed-dashboard picture. Original source runs stay within one split. Synthetic placements only use training sources and must not be counted as independent real examples. These remain same-PC, small-sample checks, not production-level evidence.

Train a separate candidate with `scripts/Train-Repair-Model.py --data <reviewed-data.yaml> --weights <trusted-local-best.pt>`. The script uses local weights, CPU and a new output directory; it does not activate, upload or overwrite the working model. Private screenshots, labels, model files, progress and results remain under ignored data folders. Verify candidate recall on real Notepad windows and false detections on unseen closed screens at the same threshold and capture size before importing it into Render. Keep the old weights for comparison.

For stronger evidence, add fresh open and closed examples from different sessions, window positions, desktop themes, resolutions and PCs. Keep a new test set out of training and model selection. Record how often closed screens trigger detections, how many open windows are missed and how quickly alerts occur. A clean result on a small demo set cannot guarantee zero future mistakes.

## First candidate result

The CPU run stopped early after 13 rounds without replacing the original weights. Its best checkpoint was exported to ONNX. PT and ONNX predictions were compared to check that lower candidate scores were not an export-only fault. At the old 0.40 confidence threshold the candidate missed the three validation positives, so it was not accepted with that setting. A 0.10 operating threshold was selected using the validation screenshots, where all three real windows were found and none of three negative screens triggered a detection.

The fixed operating point was then tested on the 12 test pictures at the browser's approximate 1280-by-720 capture limit and JPEG quality 72, with class top-1 selection and a box-overlap requirement of at least 0.50. The candidate found 6/6 real Notepad windows and falsely flagged 0/6 negative screens. The original model, evaluated at its original 0.40 threshold, also found 6/6 real windows but falsely flagged 4/6 negative screens. The supplied closed-dashboard screenshot was one of the held-out negatives. The login picture was a known training hard negative, so its improvement is a regression check, not independent test evidence.

The upload copy is `data/model-repair/ready-to-upload/Notepad-Repaired.onnx` (approximately 10.1 MB). Its companion `evaluation.json` records the operating settings, predictions and checksum. Set detection confidence to **0.10**, require **2 consecutive detections**, and restart sharing after activating it. Two-frame confirmation adds a short delay and reduces one-frame alerts; it does not guarantee zero false alarms. Keep the original model. A separate live Render test and new-PC screenshots remain necessary before a stronger reliability claim.

If the existing imported model is named `model`, rename it to `Old Notepad` before importing the candidate: the current upload endpoint stores incoming weights under that generic model name. The repair does not require deleting the old weights. Ensure the browser preview-feedback fix is deployed too: review previews pause capture, and Resume monitoring hides the old picture before capturing again.

Reference: [Ultralytics training guidance](https://docs.ultralytics.com/yolov5/tutorials/tips-for-best-training-results) recommends varied, accurate labels, separate evaluation data and background examples to reduce false positives.
